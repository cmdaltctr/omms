## Goals / Non-Goals

**Goals:**

- One visible button per view that gets from "I want my chats imported" to a confirm dialog with no other decision.
- Every number the user must judge (sessions, calls, time) on one dialog, and three plain lines at the end.
- Keep every server route and the importer, the ledger and the job slot as they are.

**Non-Goals:**

- No new server route, config key or stored field.
- No change to terminal or in-session commands beyond the help text that names one.
- No pause or restart survival for manual web jobs.

## Decisions

**1. Off is a host state, driven by the switch.** Add `autoImport: boolean` to `HostStatusInput`, read from the settings snapshot that `useBackfill` already loads (`autoBackfill.globalValue`). Rules in order: not set up; running run (unchanged, a user-started run while off still reads Running); paused; failed; stopped with work pending; blocked by the server only while the switch is on; then `autoImport ? running : off`. With the switch off, a host the server reports as blocked reads Off with Turn on, not Stopped with a disabled Resume; the card line follows the same rule. Off has the action `turn-on`. **Turn on** opens a confirm dialog on the shared dialog (`TurnOnAction.tsx`) that says automatic import runs for every host and makes model calls; only its confirm button saves `{ autoBackfill: true }` through `backfill.save`. Pause and Resume keep their one-click behaviour. Card line: `Automatic import off · history imported {date}`. Reason: the switch is the only fact the header ignored. Score: likelihood 4, impact 4, product 16. Fix now, failing test first.

**2. The quick flow runs in the browser on today's routes.** For each chosen host the page posts `/imports/sessions` with `scope: "all-projects"`, `limit: 1`, `refresh: true` and the default outputs. It then sets `selection: { mode: "all", excluded: [] }` on the draft and posts the same group request it builds today with `dryRun: true`. The real import posts the identical request with `dryRun: false`. Reason: the listing gives the revision and listing time that pin the selection, so the server's staleness rules apply unchanged. A server-side builder like `recordPastTurnsRequest` was the alternative; it needs a new route and would split the draft rules across two places. The flow never throws: a listing or preview that fails ends the busy line and shows its reason. A click while a listing or preview runs starts nothing (a ref set on the click, so two clicks in one render start one listing). When the server refuses the real start because the list went out of date (a new session after the preview), the dialog closes and the flow previews once more and opens the dialog with the new numbers; a second refusal shows `New chats appeared. Select Import new chats again.` (or **Import all hosts** on the overview), never the server text.

**3. One draft for both paths.** The primary button and **Customise** share the one `ImportDraft`. When the user has not touched Customise, the draft holds the defaults. When the user listed and ticked sessions in Customise, the primary button uses that selection and skips the listing. Reason: a second draft would let the two paths disagree on what was previewed.

**4. Defaults.** `initialImportDraft` gets `scope: "all-projects"`. On the overview, a fresh draft ticks every host whose `readiness.defaultSourceFound` is true; a saved choice in `localStorage` still wins. The hosts are ticked once readiness loads, because readiness is not known when the draft is made. The saved choice moves to a new key (`omms-memory-import-hosts-v2`) and the old key is ignored, so every user gets the All projects default once; after that a saved choice wins. `modelChoice` defaults to the value from `defaultImportModel(host, backfillSetting, readiness)`: `external` for Claude Code; the backfill `provider/model` when it is listed in `readiness.opencode.models`; `external` otherwise. Reason: the web app has no session model, so `inherit` cannot run here; picking a listed model keeps one model for both imports where the web app can call it. **This changes what a user sees at first run** (scope and ticked hosts). The overview stores the host choice only after the hosts are known (a saved choice, or the readiness tick has run) and the user has changed something in the panel, so leaving before readiness loads, or never touching the panel, stores nothing; a default is never kept as the user's choice.

**5. One model line, picker in Customise.** The line reads `Model: Saved external API (deepseek/deepseek-flash) · Change`. When the host's backfill model differs, a second short sentence names it and says it is changed in the host's settings card further down the page. No new anchor is added, so `settings-navigation.ts` and `HostSettings.tsx` stay untouched. The import model `Select` stays in `HostSessionSelection`, which now lives in Customise, and loses the `None` option. Reason: `None` could only block the run. Model row reasons for the external API are plain sentences with no config key (`memoryModel`, `memoryApiKey`, `env://`, `file://`) and name no host, because the external API belongs to no single host; the row links the External API card. The server's `importBlockedReason` texts change to the same sentences. **Change** focuses the model choice of the host view's host, or on the overview the first ticked host, whose section is visible. Exception to "HostSettings.tsx stays untouched": the automatic-import row gets `id="memory-section-auto-import"` for the `friendly-settings` search link; a page shows one host view, so the id is unique.

**6. Readiness checklist is a pure function.** `importChecks({ hosts, readiness, writeHealth, modelTest, draft })` returns three rows `{ id, state: "pass" | "fail" | "untested" | "unknown", text, action }` and `blocked`. Model state comes from `modelBlockedReason` (reused) plus the last test result held for the page. Memories saving comes from `useWriteHealth`. History found comes from `defaultSourceFound` and `piReader`. While readiness or write health is still loading the row reads unknown and does not block, as the server checks again at start.

**7. Test call only for the external API, once per model per page load.** `POST /api/settings/external-api/test` before the first preview. A connected OpenCode model is listed by a live OpenCode server, so it is not test-called. Each result lives in the page module, keyed by the provider, model and URL it tested (never the key), so a second host view on the same page load does not test the same model again, and a model changed in Settings in the same tab counts as untested, for a pass and for a fail. A failed test blocks the button for that model until the page is reloaded, so a broken key costs one call, not one per click. Reason: one small call proves the key and URL before a paid run, and repeating it on every click would cost money for nothing.

**8. Estimate pure function.** `importEstimate(previewJob, runs)` returns `{ sessions, calls, minutes | null }`. Calls = memory units to import (`unitsWouldImport`) plus `profileEstimate.analysisCalls`. A host's rate comes from its latest finished run record with `done ≥ 5` and `updatedAt − startedAt ≥ 60 s`, in units a minute. The server runs hosts one after another, so minutes = ceil(sum over hosts of that host's calls ÷ that host's rate). A host's calls are its own units plus its own profile calls; profile calls the host rows do not account for go to the first host, which drains the shared queue. Null when any host with work has no qualifying run, or when there are no calls. Real work never reads 0 minutes. `nothingToImport(previewJob)` is true when sessions, units, profile calls and skill turns are all zero. Reason: a fixed seconds-per-call guess would mislead; a measured rate for this machine and model is better, and "known once it starts" is honest when there is none.

**9. Confirm dialog on the shared Dialog.** `ImportConfirmDialog` takes the estimate and the host labels, and is the only path to `start(false)`. **Start import** in Customise opens it too. It follows the `SpaceConfirmDialog` pattern: title, one sentence, Cancel and Import, server error shown inside and the dialog stays open.

**10. Progress time left from the run record.** `ImportProgressBar` takes the active child's `minutesLeft` from `statuses.backfill.runs[host].run`. `useBackfill` already reloads the run records every 3 seconds, so the panel adds no reload of its own. Reason: the run record already measures the rate from the recent window; a second estimator would drift from it.

**11. Finish summary pure function.** `importSummary(job)` returns `{ saved, profilePrompts, failedUnits, profileFailed, failed }` summed over children: `summary.unitsImported`, `summary.profile.promptsRecorded`, `summary.unitsFailed`, `summary.profile.failed`. The dialog shows up to three lines, each true for the run: memories saved; "Profile updated from N prompts" only when N > 0, or "Profile learning failed"; and "Failed: N" when units failed, "Nothing failed." when nothing did, or "The import stopped before it finished." when the run stopped with no reason (a reason shows above the lines). It never shows "Profile updated from 0 prompts" or "Failed: 0". Then **Retry failed** when something failed, then a closed **Details** that renders today's `ImportResults`. The brief asked for "profile items learnt"; the importer does not count items, and a before-and-after count of the profile would mislead because the merge caps each type at 50 items. **Retry failed** clears the job view and runs the primary flow for the same hosts; on a host view it uses that host only. The progress bar names the step in plain words (Saving memories, Learning your profile) and the cancel button reads Stop after the current step; the unit counters stay in Details.

**12. Missing folders: one notice, one target.** The notice reads `{n} sessions skipped: folder missing. Resolve` from `summary.unresolved` or `page.unresolvedCount`. **Resolve** navigates to `/memory/<host>#directory-maps-<host>`. The existing `revealPageAnchor` path opens that host's list in **Sessions that need a folder** and moves focus to its summary, on a host view and from the overview alike. The `maps` text box, `draft.maps` and `parseMaps` are removed from the page, and requests send `pathMaps: []`. **BREAKING** for page users who typed run-only maps; saved maps cover the same need and Smart resolve fills them.

**13. Re-analyse opens the panel.** `MemoryOverview` sets `importOpen` and opens Customise when `profilePreset > 0`. Score: likelihood 8 (every click), impact 2 (confusing, recoverable), product 16. Fix now with a failing view test.

**14. OpenCode session titles.** `OpencodeSessionMeta` gains `title: string | null`; `readRows` maps it to `ImportSessionRow.title`; the list returns it after `stripPrivateContent` and a cut to 80 characters. The page shows it before the id. Pi and Claude Code rows show the id as today. Reason: the title is stored by OpenCode as session metadata; reading first prompts would break the "without conversation content" rule for the list.

**15. File split to stay under 500 lines.** `ImportSection.tsx` keeps the layout. The job state (refresh, poll, start, cancel) moves to `use-import-job.ts`; the quick flow (test, list, preview, open dialog) moves to `use-quick-import.ts`. New components: `ImportChecklist.tsx`, `ImportConfirmDialog.tsx`, `ImportCustomise.tsx`. New pure modules: `import-checks.ts`, `import-estimate.ts`, `import-summary.ts`. New strings go to three new tables, `i18n/import-status.ts`, `i18n/import-flow.ts` and `i18n/import-result.ts`, spread into the settings text once, so the three builder groups never edit the same lines.

**16. All-hosts terminal command: follow-up.** Reusing the grouped job path from the CLI needs a request builder with outputs (generalising `recordPastTurnsRequest`), a `SettingsImportJobs` start and wait loop, a grouped report printer, a confirmation for paid runs and a `--yes` flag. That is about 150 to 200 lines with tests and docs, above the brief's limit of about 100.

**17. Live-check fixes.** The live check found these, and each has a test.

- Waiting profile prompts alone are not work. The server marks a host with no sessions as no-work and never runs it, so the profile step cannot run in this flow. `nothingToImport` and the estimate count profile calls only when a host has sessions, and the shared profile calls are timed on the first host that runs. The page says **Nothing new to import**. Profile catch-up stays the way to learn from waiting prompts alone.
- The confirm dialog names only the hosts the preview found sessions for (`hostsWithWork`).
- The primary button never re-analyses: the quick flow previews with `force` off. Only **Start import** in Customise keeps `force`, and the dialog then says imported chats are analysed again. `HostView` no longer takes `profilePreset`, and `MemoryView` ends the preset when the page leaves the overview.
- `ImportSection` is keyed by host in `HostView`, so Customise options belong to one host view.
- Profile learning needs an email (`userEmailOverride`, else the git `user.email` of the folder the import runs in). The rule is unchanged. Readiness gains `profileIdentity`, read with the same rule from the web app's folder; the checklist shows a failing **Profile** row while User profile is on. A run that still fails for this reason says to set the email, never to refresh the preview.
- The settings checkbox **Import past chats automatically** opens the Turn on dialog (`TurnOnDialog`) when ticked; unticking saves at once.
- A failed model test shows one plain sentence by status code (401/403, 404, 429, 5xx, no connection, other) and the code as small text, never the raw reply. Customise shows the checklist's model state. The bar hides `0 / 0 · 0%` until the first count. One and many have their own strings. The OpenCode-only sentence shows on a set-up OpenCode view only. While the model is untested, a line says the button checks it with one short call first; that call is by design, once per page load or model change.

## Risks / Trade-offs

- [The quick flow lists then previews; a new session between the two makes the preview stale] → The existing stale error shows. The panel retries the listing once on a stale reply, then shows the error.
- [Large existing view specs (`memory-workspace-import.spec.tsx`, 571 lines) pin the old flow: Pi and current project default, `window.confirm`] → Rewrite those assertions to the new spec in the same group, test by test, and keep every other assertion. No assertion is dropped without a replacement that checks the new rule.
- [The time estimate is wrong when the last run used another model or ran mostly cached units] → It reads "about", uses only runs of at least 5 units over a minute, and the progress bar gives the measured time once the run starts.
- [`ImportSection.tsx` sits at 490 lines] → Decision 15 moves logic out first; `tests/file-size-ceiling.test.ts` guards it.
- [The test call costs a little money] → One call per page load, only for the external API, with the existing 64-token output cap.
- [Other changes touch the same i18n file and the Memory page] → `friendly-settings` owns Settings cards and labels, including `HostSettings.tsx`, which this change does not edit. `seamless-setup` owns the welcome panel. This change uses the existing `WebHost` and `BackfillHost` types and adds no host list.
- [Removing the map text box drops run-only maps] → Saved maps and `--map` in the terminal still cover it; the docs say so.

## Migration Plan

No data migration. The saved host choice moves to a new browser storage key, so each user sees the All projects default once; the old key is ignored. Rollback is a revert of the pull request; no stored state changes shape.
