# Design

## Context

See proposal.md for the why. Facts from the code that shape the design:

- `CleanupService.runCleanup()` (`src/services/cleanup-service.ts`) does two jobs in one run. It deletes old unpinned memories and old prompts in every shard of the active space. It also does housekeeping: prunes capture attempt records, the capture retry queue and cleanup undo records, then runs `VACUUM`. `shouldRunCleanup()` returns false when `autoCleanupEnabled` is off, so turning cleanup off also stops the housekeeping.
- The only automatic caller is OpenCode idle (`src/v2/session-events.ts:126`). Pi and Claude Code never run it. So on Pi and Claude Code, capture attempt records are never pruned today (`pruneCaptureAttempts` has no other caller).
- `ensureConfigExists()` (`src/config.ts:360`) writes `CONFIG_TEMPLATE` when no config file exists, and the template sets `"autoCleanupEnabled": true`. Most installs therefore have the key set to `true`, though the user never chose it. On Pi and Claude Code that value never deleted anything, because nothing triggered a cleanup there. Keeping it as the deletion switch while adding Pi and web app triggers would start deleting for those users after the update.
- The manual **Cleanup** button on the memory list calls `POST /api/cleanup`, which runs `runCleanup()` directly after `confirm(t("confirm-cleanup"))`. It deletes unpinned memories and prompts older than `autoCleanupRetentionDays`, whatever `autoCleanupEnabled` says, and does the housekeeping.
- `loadConfigFromPaths()` parses with `stripJsoncComments` and `JSON.parse`, and on failure logs and returns `{}`, or throws in strict reload. `buildConfig()` throws on the first invalid value (`normalizeAutoCleanupRetentionDays`, `checkedMemoryLimit`, `claudeConfigDir`, `embeddingDimensions`). A throw at module load stops the host.
- `settings-snapshot.ts:100` throws "Config file cannot be parsed" with no detail.
- `global-config-writer.ts` accepts `memoryApiUrl` as any non-empty text (generic fall-through), and has no null (clear) for `memoryApiUrl` or `memoryModel`.
- `testExternalApi(given?)` (`src/importer/external-api-test.ts`) already accepts a config object. The route passes none, so it tests the saved values. The reranker test already posts the form values.
- `src/services/web-server.ts` (1837), `src/config.ts` (912 of 927), and `src/importer/claude-hook-api.ts` (552) sit at their size ceilings. New routes go in a route module through `web-route-modules.ts`.
- `maxProfileItems` and the three `userProfileDisplay*` keys are only read inside `src/config.ts` (checked with ast-grep `$A.<key>` over `src` and `web/src`: no reads). `tests/config.test.ts:134-136` checks their types.

## Goals / Non-Goals

**Goals:**

- After the update, no memory is deleted by age on any host unless the user turned deletion on after this change, on the card with its count or by writing the new key by hand. A config file written by an older version never causes deletion.
- One behaviour per setting on all three hosts.
- A user can find, read and change the common settings without the docs.

**Non-Goals:**

- No move of whole pages. The Memory page keeps its shared cards.
- No new settings beyond exposing existing keys, except `autoDeleteOldMemories`, which replaces `autoCleanupEnabled` as the deletion switch.
- No change to the manual **Cleanup** button. It keeps its own confirm and its current behaviour (see decision 2).
- The import page, host view model pickers, directory maps, welcome panel, `setup` and `doctor` stay with their owning changes.

## Decisions

1. **A new key turns deletion on; the old key is retired.** New global-only boolean `autoDeleteOldMemories`, default `false`. Only this key lets an automatic run delete memories and prompts. `autoCleanupEnabled` is no longer read by `buildConfig` or the cleanup service: a file that sets it to `true` or `false` loads with no error and deletes nothing. `autoCleanupRetentionDays` keeps its meaning and validation. `initConfig` drops `autoDeleteOldMemories` from project overrides, as it does for `autoCleanup*` today. The template drops both old active lines and carries `autoDeleteOldMemories` and `autoCleanupRetentionDays` commented out under a warning. No automatic rewrite of the user's file. Alternatives: keep `autoCleanupEnabled` with a default of `false`. Rejected: old-template files say `true`, so Pi and Claude Code users would start losing memories after the update (Likelihood 8, Impact 9). Rewrite the template line on load. Rejected: OMMS would edit a user's file on its own. The code shows no problem with the new key: `fileConfig.<key> ?? DEFAULTS.<key>` and the dotted-key writer handle it like any other boolean.
2. **Split the run into housekeeping and deletion.** `runDailyMaintenance(deleteOld)` replaces the automatic call. Housekeeping (capture attempt records, retry queue, undo records, `VACUUM`) always runs and reads neither key. Deletion of memories and prompts runs only when `deleteOld` is true, which every caller sets from `CONFIG.autoDeleteOldMemories`. The once-a-day guard covers both. `shouldRunCleanup()` no longer checks any switch. The manual **Cleanup** button is unchanged: it keeps calling `runCleanup()`, which deletes by `autoCleanupRetentionDays` and does the housekeeping, after its own `confirm()`. A user who presses it chose deletion at that moment. Reason for the split: with deletion off, diagnostics tables must not grow without limit.
3. **One trigger per host, same guard.** OpenCode keeps its idle trigger, moved before the capture-off early return so housekeeping runs with capture off. Pi calls it without awaiting after `agent_settled`. The web app starts a 24-hour timer (`unref`) at start, which covers Claude Code, whose hooks do no memory work in the hook process. The guard is the existing per-process `lastCleanupTime`. Alternative: a run record in the store shared by all processes. Rejected for now: the deletes are idempotent, and several OpenCode processes already run it today. Interface for other groups: `cleanupService.runDailyMaintenance(deleteOld: boolean): Promise<void>` and `startDailyMaintenanceTimer(): () => void`, both in `cleanup-service.ts`.
4. **Count with the same selection.** `countCleanupCandidates(retentionDays)` and the delete loop both call `findOldMemories(cutoff)` in `cleanup-service.ts`: old unpinned memories, not memorisations, in every shard of the active space. The count deletes nothing. A run deletes old prompts and the memories captured from them together. The earlier code skipped a memory linked to an old prompt, deleted the prompt, and took the memory on the next run, so the dialog undercounted. The skip came from commit `b6a37ed5`, meant to protect memories of recent prompts, but it read links from the old prompts only; no ADR, TDR or spec records a reason for the delay (ADR-051 point 7). The dialog says the memories go at the next daily check. The Memory cleanup card writes `autoDeleteOldMemories: true` only after the confirm dialog shows this count. When the file has `autoCleanupEnabled: true` and no `autoDeleteOldMemories`, the snapshot sets `legacyCleanupKey: true` and the card shows one note: the old setting no longer deletes anything, and this switch turns deletion on. Route: `GET /api/settings/auto-cleanup/preview?days=N` in a new `src/services/settings-routes.ts`, with the same origin and token rules as other Settings routes.
5. **Config problems live in their own module.** New `src/services/config-problems.ts` holds pure helpers and the problem list:
   - `describeJsoncError(content)`: runs `jsonc-parser` `parse` with an error array, turns the first error offset into a line and column, and maps the error code to a plain sentence. Called only after the existing parse fails, so the happy path is unchanged.
   - `buildTolerant(build, fileConfig, fileOf)`: calls the given `buildConfig`. On a `ConfigValueError` (a new error class with `key` and `accepted`), it removes that key from a copy, records a problem with the key's line, and tries again, at most once per key. A first load and a live reload both use it; only a file that cannot be parsed keeps the last good settings on reload, so a bad value never freezes later edits.
   - Fail-safe keys (`FAIL_SAFE`): a rejected value for one of these turns its feature off for that load instead of using the default, and the problem says which feature is off. `autoDeleteOldMemories` and `autoCleanupRetentionDays` turn off `autoDeleteOldMemories`; `autoBackfill`, `opencodeBackfillModel` and `piBackfillModel` turn off `autoBackfill`; `autoCaptureEnabled` and `webServerAutoStart` turn themselves off; `userProfileAutoCleanupEnabled` and `userProfileAutoCleanupInterval` turn off `userProfileAutoCleanupEnabled`. `STRICT_BOOLEANS` makes `buildConfig` reject text such as `"false"` for these switches. Judged safe to default: `captureTrace`, `skillLearning` and `visibleRecall` treat anything but `true` as off or are checked as booleans with an off default; `skillLearningRedact` defaults to on (safer); `webServerHost` defaults to loopback; `rerankerEnabled` defaults to off; `deduplicationEnabled` gates only the manual Deduplicate button, which asks first; `webServerEnabled` does not change who can reach the web app, which `webServerHost` decides; retention days and hours fall back to finite defaults and delete only record rows.
   - `buildKeeping(build, config, keys)`: `validateGlobalConfig(parsed, editedKeys)` drops every rejected key outside the edit before it builds, so the Settings page refuses a save only for a bad value in the edit itself or a file it cannot parse.
   - A problem names the Settings page only for a key a card can write (`settings-editable-keys.ts`); otherwise it says to fix the file.
   - `recordConfigProblems` and `currentConfigProblems`: module state, no `CONFIG` import. Hosts import from this module, not `config.js`, because many tests stub `config.js`.
     The validators in `config.ts` and `memory-limits.ts` throw `ConfigValueError` with their existing message text, so current tests keep passing. `config.ts` stays under its ceiling: removing the four keys frees about 12 lines.
6. **Hosts show problems once.** OpenCode: `showOpencodeNotice` in `v2/startup.ts` after config init. Pi: `ctx.ui.notify(..., "warning")` in `session_start`. Claude Code uses the same contract as the `seamless-setup` change, so the two branches merge cleanly: the hook sends `"notices": true` in its SessionStart request; the web app's reply carries an optional `systemMessage` string, its lines joined with a newline; the hook copies that string to the `systemMessage` field of its one stdout JSON object and never puts it in `additionalContext`. A request without `notices` gets no `systemMessage`. This change adds one line source to that reply: the config problem sentences. If `seamless-setup` lands first, this change only adds its lines to the existing list; if this change lands first, it adds the `notices` flag and the copy in `hook-client.ts`, a few lines, and `seamless-setup` adds its lines on merge. The reply is built in `claude-hook-context.ts`, because `claude-hook-api.ts` is at its ceiling. If the web app is not running, Claude Code shows nothing; its existing health message already covers that case.
7. **Snapshot reports instead of failing.** `settings-snapshot.ts` returns `problems` and `readOnly: true` with default values when the global file cannot be parsed. The page shows the banner and disables Save. The writer already refuses invalid JSONC.
8. **New writable keys.** Add to the writer and the snapshot: `autoCaptureEnabled`, `chatMessage.enabled`, `visibleRecall`, `injectProfile`, `memory.defaultScope`, `autoDeleteOldMemories`, `autoCleanupRetentionDays`. The page never writes `autoCleanupEnabled`. The writer already maps dotted keys to the JSONC leaf, so `chatMessage.enabled` keeps the other `chatMessage` keys. `autoDeleteOldMemories` and `autoCleanupRetentionDays` are global-only in `initConfig`; the others keep their project override rules, and the snapshot shows a project value. `memoryApiUrl` must match `^https?://\S+$`. `null` clears `memoryApiUrl` and `memoryModel`.
9. **Test what is in the form.** `POST /api/settings/external-api/test` accepts an optional body `{ provider, url, model, key }`, where `key` is a reference or a pasted value held in memory only. The route builds the config for `testExternalApi(given)` and redacts the pasted value from any error. An empty body keeps today's behaviour.
10. **One key route for two settings.** The `/api/settings/external-api/key` route moves from `web-server.ts` to `settings-routes.ts` and takes `setting: "memoryApiKey" | "rerankerApiKey"`. `memory-key-source.ts` takes the file name from the setting. The Embedding card keeps sending its key inside the candidate, because Apply must test and save together. All three cards use one `KeySourceField` component. The Reranker card's Test sends a pasted key as `rerankerApiKeyValue`; `src/services/reranker-test.ts` uses it for that request only and refuses it on a network host without Basic Auth, the same rule as the External API test. The snapshot reports `resolvesInWebApp` for `rerankerApiKey` and `embeddingApiKey`, so each card says whether the web app can read its key.
11. **A settings catalogue drives rows and search.** `web/src/lib/settings-catalogue.ts` lists each writable setting: key, plain name, one-line description, default, what it affects, page and anchor. Texts live in a new `web/src/lib/i18n/settings-catalogue.ts`, merged into the Settings table the same way `openrouter.ts` is. A shared `SettingRow` renders name, description, default, affects and the key as secondary text. `SettingsSearch` filters the catalogue and navigates with the existing `navigate` and `revealPageAnchor`. Reason: one list feeds the rows, the search and a test that every writable key has an entry. Alternative: an index of links per card. Rejected: it does not find a setting by its name.
12. **Plain sentences in pure modules.** `web/src/lib/provider-names.ts` (provider id to display name) and `web/src/lib/reranker-messages.ts` (code to sentence) are pure and covered by web specs.
13. **One confirm dialog for settings.** `SettingsConfirmDialog.tsx` on the shared `ui/dialog`, following `SpaceConfirmDialog`: title, plain effect sentence, Cancel and confirm, progress and server error inside the dialog. It replaces `window.confirm` in the Embedding and External API cards and serves the cleanup and retry-retention confirmations.
14. **Embedding presets.** llama.cpp moves before Ollama, as the project rule makes llama.cpp the local default. The baseline spec listed Ollama first; the delta fixes it.
15. **Fixes after the live check (2026-11-17).** The browser check found nine defects; each fix keeps the rules above.
    - External API **Save** runs the Test call once with the form values before it writes anything. It saves only on a pass. A 401 or 403 never saves. A network error or timeout opens the shared confirm dialog: **Save anyway** or **Cancel**. An emptied URL or model turns the external API off, so that save needs no test. `testExternalApi` returns `reason` (`refused`, `not-found`, `rate-limited`, `provider`, `unreachable`, `not-configured`, `failed`) and the HTTP `status`; the card maps them to translated sentences, shows the status as small text and never shows the provider's reply. The Reranker card already shows codes only, so it needs no change.
    - Every run that deletes something, daily or from the **Cleanup** button, logs one line `Cleanup: old memories deleted` with `memories`, `prompts`, `retentionDays` and `trigger` only.
    - Cancel in the deletion dialog puts the switch back (`onCancel` on `useSettingsConfirm`). When a problem has `off: "autoDeleteOldMemories"`, the card shows the switch off with one line that points to the banner, and a save also writes the days.
    - The banner builds the sentence for a file it cannot read from the structured fields (`file`, `line`, `column`), so it translates; the file and position appear once as small text. The server's English `message` stays for the hosts and the log. The value-problem footer no longer claims "keeps the last good settings", which was wrong for a rejected value.
    - While the global file cannot be parsed, the snapshot reads the last good global file (`getLastGoodGlobalFileConfig()` in `config.ts`) and sets `valuesFrom: "last-good"`. The banner says the cards show the last settings OMMS could read, so no row claims a wrong default.
    - A search result calls `revealPageAnchor(hash, { focus: true })`, which moves focus to the card heading or the Shared row's summary.

## Risks / Trade-offs

- [OpenCode users who relied on automatic deletion lose it after the update] → Breaking, but nothing is lost: memories are kept, not deleted. The card shows a note when the file still has `autoCleanupEnabled: true`, and `docs/upgrading.md` says how to turn deletion on again.
- [A test that only checks the default would miss the old-file case] → Tests 2.1 and 3.1 to 3.3 load a file with `"autoCleanupEnabled": true` and no new key on each trigger path, with a mutation step that makes the trigger read the old key and must fail.
- [Several processes can run the daily job on the same day] → Deletes and prunes are idempotent; this matches today's OpenCode behaviour. A shared run record is a possible follow-up.
- [Tolerant loading hides a bad value behind its default] → Every host shows the problem, and the Settings page banner names the key and range. A fail-safe key turns its feature off instead.
- [Deletion goes one run sooner for memories linked to old prompts] → Same set as before, one day earlier; the confirm dialog shows that number.
- [A pasted key in a test request] → The key stays in memory for that request only, is never logged, and is redacted from the reply, as the embedding test already does.
- [Shared i18n file conflicts between branches] → New strings go in a new file. Only the Settings cards group edits `i18n/settings.ts`, for changed wording only.
- [`web-server.ts` at its ceiling] → The key route moves out, which frees lines for the timer start and the module hook.

## Migration Plan

- No data migration and no file rewrite. An old config file loads unchanged, including `autoCleanupEnabled` and the four removed keys.
- Rollback: revert the change. The old code ignores `autoDeleteOldMemories` and reads `autoCleanupEnabled` again, so a rollback restores the old OpenCode behaviour for files that still have it.
