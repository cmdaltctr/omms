# Design

## Context

Facts checked in the code on 2026-11-16 (worktree at `8da0072f`):

- `src/cli/index.ts` dispatches subcommands by name; there is no `setup` or `doctor`. The package has one bin, `om-memory-system` → `dist/cli/index.js`. `runCli` first calls `handOffOrRegister`, so an `npx` copy records itself and hands off to a newer recorded copy.
- Self-update already shells out to each host: `opencode plugin update om-memory-system` (`src/adapters/opencode/self-update.ts:31`), `pi update npm:om-memory-system` (`src/adapters/pi/self-update.ts:27`) and `claude plugin marketplace update omms` plus `claude plugin update omms@omms` (`src/adapters/claude-code/plugin-self-update.ts:44-51`). They run detached with `shell` on Windows and a 120 s timeout. `readPiSettings` (Pi `settings.json`, honours `PI_CODING_AGENT_DIR`) and `unpinnedPackageSource` already parse Pi's package list.
- `findOpencode` (`src/importer/opencode-standalone-models.ts:75-98`) already searches `PATH`, `PATHEXT` and known install folders for the `opencode` binary.
- `opencode plugin add` (OpenCode 2.1.2, read from the installed binary): for a package with a server or GUI entry it writes only the global `opencode.json(c)` and prints "installed and added to <path>" or "already configured". It writes `cli.json` only for a TUI-only package. OMMS has a server entry, so `plugin add` never writes `cli.json`. `opencode plugin update <target>` fails with `Plugin is not configured` when the target is in neither the server's plugin list nor `cli.json` `plugins`. The OpenCode docs say `cli.json` is created by OpenCode, rejects unknown keys, accepts a `plugins` array, and that an absent `cli.json` makes the first V2 start migrate old `tui.json` settings.
- The Claude Code hook maps `ensureWebApp` results `port-busy` and `no-runtime` both to `server-unreachable` (`hook-client.ts:382-383`). `web-ensure.ts` already returns the two separately.
- Pi starts the web app with `budgetMs: 0, wait: false` and drops the result (`src/adapters/pi/extension.ts:186-214`). `port-busy` and `no-runtime` are still decided before the spawn, so the result is known. OpenCode turns the same results into notices (`src/v2/startup.ts:124-130`); `showOpencodeNotice` writes to the console, which goes to the OpenCode log, because the V2 server plugin has no toast API. The OpenCode terminal interface has a `notify` callback (`src/adapters/opencode/tui-status.ts:40`).
- Claude Code capture readiness is `resolveClaudeCodeLiveModel(CONFIG)` (`ready`, `issues`). The status line mod polls `/api/health` every 30 s and maps `success` to `connected` (`hooks/omms.jsx:65-90`). `/api/health` is open without a token and lives in `src/services/web-server.ts`, which is at its 1837-line ceiling.
- `webServerAutoStart` defaults to `true` (`src/config.ts:264`). OpenCode and Pi call `reconcileWebAutostart` at each start, which reinstalls the login item while the setting is on; Claude Code never calls it. `autoBackfill` defaults to `true`; Claude Code starts its backfill at the first `SessionStart` and only with a ready external API. The local embedding model `Xenova/nomic-embed-text-v1` downloads into `<global storage>/.cache` unless `embeddingApiUrl` is set.
- Settings health rows (`src/importer/settings-health.ts`) have `check`, `status`, `reason`. The Claude Code rows always run. The route is `POST /api/settings/health` with the local token.
- The Memory page empty state is one line in `MemoryList.tsx:71-74`. `GET /api/stats` gives the space total. `GET /api/settings` gives `effective` readiness for all three hosts. `App.tsx` is 491 lines.

Audit findings that were wrong or need care:

- The audit said `opencode plugin add` might write `cli.json`. It does not (checked above).
- `docs/web-ui.md:12` is wrong as the audit says, and the fix must name the config key: `om-memory-system web uninstall` alone does not keep the login item off, because the next OpenCode or Pi start reinstalls it while `webServerAutoStart` is `true`.
- The audit's hook-stdout issue (first-run "Created config template" from the hook) is scored 2 × 1 = 2 and stays out, as the audit proposed.

## Goals / Non-Goals

**Goals:**

- One command installs OMMS into every host on the computer, safely and twice-safe.
- One command tells the user what is wrong and how to fix it.
- Claude Code users see that capture is off and what to do.
- Every host says when the web app cannot start, and states once what OMMS does on its own.

**Non-Goals:**

- No new config keys and no changed defaults.
- No change to the Settings cards or the import page.
- No uninstall command.

## Decisions

1. **Host setup code lives in each adapter.** Each adapter gets a `setup.ts` that exports one `HostSetup` object: id, display name, homepage, binary name, extra install folders, minimum version, whether the host installs the login item (`loginItem`), `registered(deps)`, `installSteps(deps)` (argv lists), `nextStep(facts)` and, for OpenCode, `fileChecks(deps)` (the `cli.json` entry as a `SetupFileCheck`). `src/core/host-setup.ts` holds the type only. `src/cli/host-setups.ts` lists the three objects; the CLI may import adapters (it already imports `adapters/claude-code/hook-command.js`). Reason: no new `if (host === …)` branch outside `src/adapters/`, which the `modular-boundaries` ratchet counts.
2. **Install through the host's own command, never by editing host config.** OpenCode `opencode plugin add om-memory-system`; Pi `pi install npm:om-memory-system`; Claude Code `claude plugin marketplace add https://github.com/cmdaltctr/omms.git` (skipped when `claude plugin marketplace list` names `omms`) and `claude plugin install omms@omms`. The commands sit next to the update commands in each adapter's `self-update.ts` and use the same spawn options (`shell` on Windows, `windowsHide`, 120 s timeout), but run synchronously with captured output so `setup` can report a failure. The one exception is the OpenCode `cli.json` entry (decision 4).
3. **"Already registered" is read from the host, read-only.** OpenCode: the global `opencode.json` or `opencode.jsonc` under `$XDG_CONFIG_HOME/opencode` or `~/.config/opencode` lists a `plugins` entry whose package is `om-memory-system` (bare, with a version, or the object form). Pi: `readPiSettings` lists a package whose source is `npm:om-memory-system` with or without a version (a new helper beside `unpinnedPackageSource`). Claude Code: `claude plugin list` output names `omms@omms`. Running twice therefore runs no install command.
4. **OpenCode `cli.json`: add to an existing file only.** Merge rule: parse with `jsonc-parser`; if the root is an object and `plugins` is absent or an array with no entry naming `om-memory-system` (string or `{package}`; any version), insert the string `"om-memory-system"` at the end with `jsonc-parser` `modify`/`applyEdits`, so comments, order and other keys stay; write to a temp file in the same folder and rename. `apply()` reads the file again and merges again, because the question and `opencode plugin add` run between detection and the write; it writes only when the merge still says `add`. It resolves the path with `realpathSync` and puts the temp file beside the real file, so a symbolic link (Stow, Home Manager) stays a link, and it keeps the file mode. Never create the file: an absent `cli.json` triggers OpenCode's `tui.json` migration, and an OMMS-made file would stop it. A parse error or a non-array `plugins` changes nothing and reports the manual step. The manual step for a missing file never says to create it. Reason: `plugin add` does not write it (checked), and the update path needs it.
5. **Consent: one question for the whole plan.** `setup` prints the full plan (commands, files, first-run notice), then asks `Set up OMMS in these hosts? [y/N]`. `--yes` skips it; `--dry-run` prints only. A non-interactive standard input without `--yes` prints the plan and exits 1. Reason: simplest rule that never changes a host without a yes. Per-host choice is a follow-up.
6. **Program lookup is shared and injectable.** New `src/services/find-program.ts` finds a binary by name over `PATH`, `PATHEXT` and given extra folders, with every input passed in. Each `HostSetup` names its extra folders (`~/.opencode/bin`, `~/.pi/agent/bin`, `~/.local/bin`). Tests pass a scratch `PATH`, a scratch home and no system folders, so no test finds a real host. `findOpencode` is left as it is.
7. **Version check.** `<binary> --version` with a 10 s timeout; the first `x.y.z` in the output is the version. Minimums: OpenCode 2.0.22 (the footer needs it; earlier V2 builds load OMMS without it), Claude Code 2.1.295 (the plugin module needs it), Pi 0.86.1 (the tested version; Pi publishes no other floor). Below the minimum: `doctor` fails the row; `setup` warns in the plan and still installs.
8. **`doctor` reuses Settings health through the web app.** `doctor` probes `/api/health` (the shared `web-ensure` probe, exported) and classifies OMMS, another program, or nothing. When OMMS answers, it calls `POST /api/settings/health` with the local token (`getOrCreateAuthToken`, as the hook does) and `testModels: true` unless `--skip-model-test`. The health run already makes at most one external API call. Rows gain two optional fields in `settings-health.ts`: `host` (`opencode`, `pi`, `claude-code`) and `fix` (plain words). `doctor` drops rows whose `host` is not found and maps the rest into its table. When the web app does not answer, these rows are "skipped" with the fix to start it (`npx om-memory-system@latest web`). When it answers but the health request times out, is refused or fails, the rows are "skipped" with a plain reason (no error class name) and the fix to select Run checks on the Settings page or use `--skip-model-test`. `doctor` sends Basic Auth the way the hook does when `webServerAuthPassword` is set. A model test row that the web app cannot run because the host uses its own model (`hostModelOnly` on the health row: the Pi row when Pi is not on the external API, and the OpenCode row for an OpenCode signed-in model) becomes "skipped" with no fix in `doctor`; the Settings page still shows it as a warning. Reason: one source of health truth; the CLI loads no embedding model and no store of its own. The Settings page ignores the new fields for now.
9. **Doctor output.** Plain table to standard output: status word, check, reason, then an indented "Fix:" line. `--json` prints one array of `{check, status, reason, fix, host}` and nothing else on standard output; warnings go to standard error. API keys are redacted with `safeHealthError` as today.
10. **Claude Code capture state goes on `/api/health`.** A new pure `claudeCaptureState(config)` in `src/services/claude-capture-state.ts` returns `off` (when `autoCaptureEnabled` is false), `ready`, or `needs-setup` from `resolveClaudeCodeLiveModel`. The health body moves out of `web-server.ts` into a small `healthBody()` helper that adds `claudeCapture`, so `web-server.ts` shrinks. The mod reads it at each 30 s poll and shows `capture off` for `needs-setup` only; a missing field counts as `connected`. Reason: the poll already runs, so the label clears within 30 s of saving a key, with no new route. The state carries no secret.
11. **User-facing lines in Claude Code use the hook's `systemMessage`.** Claude Code shows a hook's `systemMessage` to the user and keeps it out of the model context; `additionalContext` goes to the model. The hook prints one JSON object that may hold both. Sources: (a) the web app's retrieve answer gains an optional `systemMessage` string and `noticeKeys` list for `SessionStart` when the request has `"notices": true`; it holds the first-run notice and the capture setup line that are not yet recorded. The retrieve request records nothing. After the hook has written its JSON line, it sends the keys to `POST /api/claude/notices` (2 s budget, errors ignored), and only then does the web app claim them. A lost first reply (cold start past the 3 s budget) therefore shows the lines again at the next session. (b) The hook itself writes the web-start failure line when `ensureServer` returns `port-busy` or `no-runtime` on `SessionStart`. Reason: keeps the one-JSON-on-stdout rule, needs no mod change, and an old hook never claims a line it cannot show.
12. **Claude Code setup line marker.** The capture setup line is claimed in the first-run record under the key `claude-code-capture-setup`, when the hook confirms it (decision 11). When a `SessionStart` finds capture `ready`, the key is cleared, so a later loss of the key shows the line once again.
13. **First-run record.** New `src/services/first-run-notice.ts`: `firstRunNoticeLines(config, { loginItem })` builds the lines from config (leaves out a part that is off; leaves out the login item when the caller passes `loginItem: false`, as Claude Code does, so the shared module holds no host-name branch), and `claimNotice(key, folder, fs)` reads and writes `first-run-notices.json` in the global storage folder (`skillStoragePath ?? storagePath`), atomically, and returns true once per key. `noticeClaimed(key, folder, fs)` reads a claim without writing, for the OpenCode server plugin. `clearNotice` forgets a key. No `CONFIG` import. Errors return false and log a code. It holds no handle, so it needs no `resettable()`. Existing users see the notice once after they update; this is accepted, because they may not know about the three behaviours either.
14. **First-run notice delivery per host.** Pi: `ctx.ui.notify(…, "info")` at `session_start` when `ctx.hasUI`. OpenCode: the terminal interface (`opencode/tui.tsx` through `tui-status.ts`) claims the key and shows the notice with `notify`. The server plugin never claims it; it writes the notice lines to the OpenCode log at each start while the key is unclaimed, so `opencode serve` and OpenChamber users find it in the log. Users without a terminal interface also get it from `setup` and the docs. Claude Code: decision 11.
15. **Shared web-start wording.** New `src/services/web-start-notice.ts`: `webStartNotice(result, port)` returns `{level, text}` for `port-busy` and `no-runtime`, else null. OpenCode `startup.ts` uses it in place of its two literals; Pi uses it in the `.then` of its existing start call and notifies once per result per process; the hook uses it for decision 11(b).
16. **Welcome panel without a new route.** `WelcomePanel.tsx` renders inside `MemoryList`'s empty branch, so `App.tsx` grows by one line only. It shows only when the list's `totalItems` is 0 and no search, label or project filter is active (`MemoryList`'s `isSearching` and `activeKeyword`, plus a new `activeTag` prop that `App.tsx` passes from `explorer.selectedTag`; one added line). It needs no `/api/stats` request. It then reads `GET /api/settings` `effective` for the three host lines, and links to `/settings#settings-section-external-api`. A host that needs setup shows its missing settings in plain words ("model", "API URL", "API key") from `src/shared/setting-words.ts`, the same pure mapping the Claude Code setup line uses, in English, Chinese and Arabic. Strings go in a new `web/src/lib/i18n/welcome.ts`, merged in `translations.ts` with one line.
17. **Docs use `npx` forms.** Every fix that names a terminal command, in docs and in `doctor`/`setup` output, uses `npx om-memory-system@latest <command>` unless the text is about the global install.

## Risks / Trade-offs

- **`systemMessage` display.** The design depends on Claude Code showing a hook's `systemMessage` to the user at `SessionStart`. The live check in task 9 confirms it on Claude Code 2.1.295 or later. If it does not show, fall back to a `$.ui.toast` from `hooks/omms.jsx` driven by the same health field, and record a TDR.
- **`claude plugin list` text format** may change. The match is the literal `omms@omms`; a miss only means `setup` runs `plugin install`, which Claude Code answers as already installed.
- **`cli.json` written while the terminal interface runs.** OpenCode reloads valid edits; the write is atomic, so it never sees half a file.
- **Version skew.** A new hook with an old web app gets no `systemMessage` and no `claudeCapture`; both fall back to today's behaviour. An old hook with a new web app never claims a line (the `notices` flag).
- **Existing users see the first-run notice once** after the update.
- **Pi notice spam.** Pi notifies at most once per result per process.
- **Windows.** Host commands run with `shell: true` as the self-update does. Fake binaries in tests need a `.cmd` shim on Windows; the tests write both.
- **Shared files.** `translations.ts` gets one import line, `web-server.ts` one replaced block. Other changes in this run touch the same files; the edits stay local.
