Does persistent memory make coding agents better, and at what token cost?

A visual guide to one paper, with two studies on two harnesses. OMMS is the system under test. Nothing here has run yet.

The whole work, start to finish

Each stage has a gate. Do not move on until the gate passes. Cost per run stays unknown until stage 2.

How memory reaches the agent

Both paths start from the finished task and end in the next task's prompt. The digest step is the difference under test.

Digest arms, D

Earlier task endsTranscript is saved
→
Model digests itA chat-model call. Its cost counts.
→
Short memoriesStored by OMMS
→
RetrievePlain, reranker or hybrid
→
InjectInto the next prompt

Raw arms, R

Earlier task endsTranscript is saved
→
Cut into windows256 tokens, 32 overlap. No chat model.
→
Raw windowsStored by the study harness
→
RetrieveSame method as its D partner
→
InjectCapped at what D injected

Why the cap: digested memories are short, and raw windows would fill any limit. The cap makes the token budget equal for real. Run D first for each repository, then cap R at D's mean tokens per recall.

Main test: preferences broken in the first answer, block 3, P against M. M cannot carry across projects by design, so the paper also compares P and M inside one project (tasks 3 and 4). Not tested: retirement on contradiction, because the scripted user never changes their mind.

What gets measured

Four layers. If the agent does not improve, the lower layers show why.

1
Memory quality
Can retrieval find the right items? Existing experiments.
2
Context quality
Coverage: did the text hold what the task needed? Utilisation: did the agent use it?
3
Agent outcome
Pass rate per task, recall probes, preferences broken.
4
Token cost
Input, cache write, cache read and output, plus OMMS's own capture calls.

Each runs on Pi and on Claude Code, so 6 in all, with a Holm correction. Cost and the other arms are estimates with intervals. The study cannot see pass-rate gaps below roughly 8 points (a rough estimate).

What the paper can say

Each result is publishable. The most likely Study 1 headline is "no detectable effect on pass rate at this size".

If this happensThe paper says
D beats N on pass rateMemory improves outcomes on independent issues, at a stated token cost.
D and N look the same, probes favour DMemory carries facts forward, but this does not show as more tasks solved at this size.
R at least as good as DThe digest does not earn its cost in coding. This extends the chat finding. The raw-RAG paper's evidence points this way, so OMMS may lose.
D beats RDigesting helps in coding, unlike chat.
P beats M after a project changeUser memory carries across projects where project memory cannot.
P costs more than it savesFollowing preferences has a token price. The oracle arm gives the reference.

Who builds what

OMMS change: cost ledger

  • Read token usage per turn, on Claude Code and Pi
  • New ledger store with no text
  • Keep the tokens of capture calls
  • Log recalled ids and bytes cut
  • Route to ask whether capture has finished

OMMS, for arm D-H

  • BM25 index over memory text, behind a setting

OMMS change: persona

  • Extend or replace the user profile
  • Lifecycle rules and budgeted injection
  • Readable user-persona.md with undo

Study harness, outside OMMS

  • Runner and scripted user
  • Raw-turn indexer, one transcript reader per harness
  • Injector plugin for Pi and Claude Code
  • BM25 for arm R-H
  • Grader wrapper and analysis

Lives in experiment folder 29. Needs no OMMS spec change.

Decisions recorded

  2. Capture model: DeepSeek flash, the current OMMS setting.
  3. Where to run: start on the Mac. Rent x86 Linux if the pilot is too slow.
  4. Access and budget: API key by default, subscription login retested in the pilot. Set the limit after the pilot. Fallback is 3 repositories (756 runs per harness).
  5. The 10 preferences: approved. The persona pilot filters them.
